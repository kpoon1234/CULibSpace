## Commands

This app lives in an npm-workspaces monorepo (`apps/frontend`, `apps/backend`). Run commands either from the repo root with `--workspace=apps/frontend`, or directly from this folder.

```bash
# from repo root
npm run dev:frontend          # next dev, this workspace only
npm run dev                   # runs both frontend and backend dev servers together

# from apps/frontend
npm run dev
npm run build
npm run start
npm run lint                  # eslint (flat config, eslint.config.mjs)
```

No test runner is configured yet (no Jest/Vitest, no `test` script) — set one up if you're asked to add tests, rather than assuming one exists. CI (`.github/workflows/pr-check.yml`) only runs `npm run build --workspace=apps/frontend` for this app, with `NEXT_PUBLIC_API_URL` set to the backend's local URL — it does not run `npm run lint` here.

Root-level `lint-staged` runs `prettier --write` on staged files under `apps/**` (`.prettierrc`: single quotes, semicolons, 100 print width) via the Husky `pre-commit` hook — don't hand-format against different rules.

## Architecture

- Next.js App Router (`app/`). `app/layout.tsx` is the root layout: it mounts the persistent `TopMenu` header above `{children}` for every route, and sets up the Geist fonts as CSS variables consumed from `globals.css`.
- Path alias `@/*` maps to this folder's root (`tsconfig.json`), e.g. `@/components/Login/Customicons`.
- Styling is Tailwind v4 via `@tailwindcss/postcss`, configured CSS-first in `app/globals.css` (`@theme inline`, no `tailwind.config.js`). Dark-mode color overrides are declared with `@media (prefers-color-scheme: dark)` in the same file.
- `components/` is organized by feature/page area, not by shared-UI type: `HomeComponent/` (home page banner), `Login/` (login form pieces), `Topmenu/` (site header). Follow this grouping when adding components rather than introducing a generic `ui/` bucket.
- The login page (`app/login/page.tsx`) is a client component with two roles, `user` and `admin`, toggled by local state — not by route or middleware. Admin submits credentials to a role-specific endpoint (`/api/admin/login` vs `/api/login`); the choice of endpoint, not client-side logic, is what tells the backend which login path to validate. The user-role path and the "Sign in with Google" link (`/api/auth/google`) are UI stubs only — submit handlers currently `console.log` the payload rather than calling the backend.
- Frontend-backend integration is not yet wired beyond that endpoint routing convention; the backend app lives at `apps/backend` in this same workspace, and CI supplies `NEXT_PUBLIC_API_URL` at build time for it.
- Some in-repo comments (e.g. `components/Topmenu/topMenuItem.tsx`, `app/login/page.tsx`) are written in Thai — this reflects the target audience (a Chulalongkorn University library system) and is intentional, not a language error to "fix".
